## What is true now

**The charts move.** That was the boss's complaint — "these so-called live cards, I never
see the data refresh" — and it had three separate causes, fixed in order:

1. A chart series could not be *expressed* as state. The validator rejected
   `items.type: ["number","null"]`, the very schema a series with gaps needs. (`669982b`)
2. The renderer handed the web leaf its props verbatim, so a bound series arrived as the
   binding object. (`0afe146`)
3. The wall drew a chart only when the panel declared `summary.seriesPath`, and no panel
   ever has. It now falls back to the first chart in the panel's own spec. (`7e12924`)

A `null` renders as a break in the line, confirmed by eye in both the detail view and the
wall tile.

**One renderer, two platforms.** 1757 lines moved from the macOS app into HibossKit; only
the two web-leaf files needed platform variants. iOS Home now carries a tile wall.
(`8d70dd9`)

**The two validators agree on paths.** A differential test now shells out to the real CLI
binary and compares JSON Pointers against the TypeScript validator, so they cannot drift
apart silently. (`3db318e`, `cbadbc1`)

## Open

**Two decisions that are the boss's, deliberately not made:**

- Unknown top-level publication keys: the server accepts them, the CLI rejects them. A
  forward-compatibility policy question, not a defect. Pick one and make both match.
- Card layout. The Apple Health reference (large coloured number, unit beside it, context
  label above, compact sparkline below, disclosure chevron, two-column grid) is not applied.
  Tiles currently have a lot of empty space under the metric.

**Two known defects:**

- On iOS, an empty attention state fills most of the screen and the first panel sits below
  the fold. The wall renders; it is placement, not rendering.
- `PanelRenderer` still requires a `webModel` that `renderWebLeaf` ignores — each
  `PanelWebLeafSlot` owns its own. Dead seam from the move, flagged by the audit.

**One unfinished check:** whether chart binding reached production. Now that the CLI and
server agree, the CLI's local pre-check rejects anything the server would, so probing
requires POSTing straight to `/api/panels` with the agent key from
`~/Library/Application Support/hiboss/config.json`. The deployed bundle does contain the
code (grep of the dry-run output); what is missing is the behavioural confirmation.

**Not built:** iOS shows no panels from the server yet (the wall there is fixture-driven),
and structured questionnaires with typed answers remain designed and unbuilt.

## Traps worth not rediscovering

- **An ad-hoc signature makes the keychain prompt return after every rebuild.** Build with
  `HIBOSS_SIGNING_IDENTITY="Developer ID Application: MEET SOFTWARE COMPANY LIMITED
  (YX8SMYQJ6U)"`; `codesign -dv` should show `TeamIdentifier`, not `Signature=adhoc`.
- **`hiboss panel publish` validates locally first.** A rejection without
  `(422 Unprocessable Entity)` never reached the server. This was misread once tonight as
  evidence that production was running stale code.
- **The cargo disk guard only counts `~/.cargo-target/*`.** SwiftPM `.build` inside aid
  worktrees is invisible to it. Twenty-six worktrees held 5 GB while the guard's own list
  showed nothing above 2.2 GB. Reclaim worktrees at merge time.
- **A test that fails to compile is not a red test.** Twice tonight a new test "failed" on
  main only because it called a function that did not exist yet. The parity test is the
  counter-example: it fails on main for the reason it is meant to catch.

## Prior art

`docs/live-panels/prior-art.md` records why we did not adopt Google's A2UI: its BasicCatalog
v1.0 has no chart component, and its 1536-line spec contains no epoch, resync, concurrency,
authority or persistence concept. It shares our data model — structure separated from state,
JSON Pointer binding, patches into a mounted tree — which we arrived at independently.
