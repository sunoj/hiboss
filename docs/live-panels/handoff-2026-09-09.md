# Handoff — Live Panels, 2026-09-09

Two production deploys, both verified by running them. The wall is empty on purpose:
every development-era card was retired at the end of the day.

## What is true now

**An agent can drive a card from a tool-call loop.** That was the blocking defect:
`stream` never released its producer lease, so a second one-shot update inside the
45-second window was refused with `lease_conflict` — the same error a genuine rival
producer gets, which made one agent look like two. The relay now has `lease.release`,
`hiboss panel update` does claim → write → ack → release in one command, and
`complete|fail|cancel|pause|resume` read the current versions and fill the compare-and-set
fields themselves. `panel doctor` checks the relay ticket really advertises
`lease.release` rather than trusting a version string both servers report.

Measured in production: three updates in seven seconds, all accepted, and the checkpoint
then showed a null lease expiry.

**A card only stays on the wall if someone says so.** Publication declares `ttlSeconds`
(default 3600, range 60..604800) and the server stores the resulting `expiresAt`.
Observations do not touch it. Renewal is a separate owner-only, version-checked operation,
refused on a terminal card, reached through `hiboss panel renew`. A lapsed running or
paused card leaves the active wall without its task state changing, because inferring
failure from silence would misclassify a healthy task during a network partition. Pins
override it; terminal cards keep their own retirement.

Measured in production: an observation changed the task values and left the deadline
untouched; an explicit renewal moved it; a renewal carrying a new window replaced it.

## The lifecycle design had a hole, and it was deliberate

`lifecycle.md` said plainly that task state never changes on lease expiry and that an
abandoned run stays running and offline until its owner reports an outcome or the boss
archives the card. The principle is right. The conclusion drawn from it — that the card
must therefore stay visible forever — was not, and it quietly made cleanup a manual chore.
The same document already had the missing piece: timed retirement is derived visibility,
not a write. Expiry is that mechanism applied to running cards.

A first attempt at this added an `expired` terminal state and a background sweep, which is
exactly the automatic-failure-on-timeout the design warns against. It was stopped before
it wrote code. Renewal being explicit, rather than implied by any observation, then deleted
a whole mechanism: the derived expiry, the observation timestamp written into the panel
row, and the 30-second coalescing floor that write had needed.

## Two defects caught by looking, not by testing

Both suites were green in each case.

- **A migration that would have emptied the wall.** Migration 0037 originally measured each
  card's window from `created_at`. Every running card in production was a day or two old,
  so the window was already spent and the first deploy would have hidden all of them at
  once — from the outside, indistinguishable from a deploy that deleted data. Check a
  backfill against real row ages before applying it.
- **A chart that drew nothing.** The card layout round removed the sparkline's point
  markers. A null splits a series into segments, and a segment holding one point draws no
  line, so `bound-chart.json` — the fixture that exists to prove null gaps render — became
  an empty box. Sparse series with real gaps are the normal case here, not an edge case.

## Also shipped

Wall cards follow the Health summary layout: context label above, large coloured value with
its unit, compact sparkline below, chevron, two columns, and heights that follow content so
nothing sits under a card's footer. On iOS the all-clear state no longer reserves 360 points
when there are cards to show, so panels are visible without scrolling. Screenshots of both
platforms are committed.

## Not verified

The wall's hiding rule is covered by unit tests over task state, placement, expiry and the
server clock, but no card was watched disappearing on a device.

## Next

Structured questionnaires with typed answers, chosen deliberately and deliberately not
started today. Today's panel forms capture answers on the device only and must never be
described as durable submissions. Read the request rules in `lifecycle.md` first: several
are settled, including that `needs_input` is derived from open blocking requests rather than
being a task state, that terminal commands carry `openRequests: reject | withdraw` with
reject as the default, that completing with an unanswered request never implies an answer,
that accepted answers are immutable, and that an answer racing a terminal transition
resolves in D1 with neither side silently converted into approval. Atomic request withdrawal
and those submission races are what remain unbuilt.

Two decisions still belong to the boss: unknown top-level publication keys, which the server
accepts and the CLI rejects, and whether a pinned card should really outlive its expiry.
