## Findings

1. **FAIL: Quiet-hours time editing mixes a wall-clock `HH:mm` domain value with device-local `Date` conversion and accepts malformed input.** `QuietTime.date(from:)` accepts any colon-split integers, defaults missing hour/minute to `0`, and falls back to `Date()` when `Calendar.current` cannot build a date (`ios/App/Settings/QuietHoursSection.swift:68`, `ios/App/Settings/QuietHoursSection.swift:70`, `ios/App/Settings/QuietHoursSection.swift:72`, `ios/App/Settings/QuietHoursSection.swift:74`). The `DatePicker` binding then saves `Calendar.current` hour/minute back into a preferences object whose persisted `timezone` may be different from the device timezone (`ios/App/Settings/QuietHoursSection.swift:54`, `ios/App/Settings/QuietHoursSection.swift:56`, `ios/App/Settings/QuietHoursSection.swift:57`, `ios/App/Settings/QuietHoursSection.swift:78`). This is a type/unit mismatch class: the domain stores wall-clock strings plus an explicit timezone, but the UI edits through an absolute `Date` in the device calendar. `.with(...)` does preserve timezone/days (`ios/App/Settings/PreferencesStore.swift:110`, `ios/App/Settings/PreferencesStore.swift:114`, `ios/App/Settings/PreferencesStore.swift:115`), but the parse/binding layer can still silently normalize bad values such as missing components or invalid times.
