## 2. Authentication surfaces and route use

| Surface | Credential → resolved context | Authorization distinction |
| --- | --- | --- |
| `apiAuth` | SHA-256 of bearer → `api_keys.key_hash`; sets `agentId`, updates key `last_used_at`. | Does not resolve a boss or role. `server/src/middleware/auth.ts:75`. |
| `bossAuth` | SHA-256 bearer → non-revoked `boss_tokens` joined to `bosses`; sets `bossId`, `bossTokenId`, `bossRole`, `bossName`; updates token use time. | Does not set `agentId`, even when `bosses.agent_id` exists. Role is read from the boss on authentication. `server/src/middleware/auth.ts:89`. |
| `dualAuth` | Tries agent key first, then live boss token; sets the corresponding context only. | Neither automatic boss-as-agent conversion nor a combined identity. `server/src/middleware/auth.ts:109`. |
| Agent admin | **Not a middleware exported from `auth.ts`.** `adminRouter` runs `apiAuth`, then queries `api_keys.role === 'admin'`. | Applies to key/channel admin routes, not all agent routes. `server/src/routes/admin.ts:12`. |
| Boss admin / write roles | Boss routes check `getBossRole`; many writes allow admin/manager and reject viewer. Boss CRUD/access/token rotation require admin. | Boss `admin` normally sees all `api_keys`; manager/viewer use `boss_agent_access`. Panels instead require explicit access. `server/src/routes/bosses.ts:34`, `server/src/routes/boss-writes.ts:193`, `server/src/routes/boss-api.ts:52`, `server/src/panels/lifecycle/repository.ts:19`. |
| Device signing | Bearer authentication first; registered key is selected using `bossTokenId` for supported signed actions. | Reply and questionnaire verification are route-level checks, not general authentication middleware. `server/src/message-security/boss-message.ts:27`, `server/src/panels/requests/signature.ts:15`. |
