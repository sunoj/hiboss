# hiboss 全案 UI 设计需求文档

> 交付对象：UI 设计师
> 版本：基于 hiboss CLI v1.6.9 / server / mcp v1.3.0 / macOS "HiBoss Island" 现状整理
> 设计范围：① 重设计现有 **macOS App**　② 新立项 **iOS 客户端**　③ 新立项 **Web 管理后台**

---

## 一、产品是什么（一句话 + 电梯陈述）

**hiboss = "AI 智能体 ↔ 老板" 的消息通信工具。**

AI 智能体（如 Claude Code）在干活时，需要向它的"老板"汇报进度、请求批准、提问；老板通过熟悉的聊天工具（Discord / Telegram）收到消息并回复，回复实时流回智能体。同时，一个智能体也可以充当另一个智能体的"老板"，从而构成**人可随时介入的多智能体自治协作网络**。

- **谁是老板**：人类，或另一个智能体。
- **谁是员工**：一个或多个正在运行的 AI 智能体会话（Claude Code sessions）。
- **核心价值**：让"无人值守的 AI 干活"变成"关键节点有人拍板"——既自动化，又可控。

### 目标用户
1. **技术型个人 / 独立开发者**：自托管一套，用手机随时批准/驳回 AI 的关键决策。
2. **管理多个 AI 会话的人**："老张式"的编排者，需要一块看板同时盯多个智能体。
3. **智能体本身**：作为 boss 审阅下级智能体产出（无人参与时自治运转）。

### 产品调性关键词（供设计定调）
克制、专注、可信赖、"驾驶舱/指挥台"感、状态一目了然、消息可秒读秒回、深色友好、通知不打扰但不遗漏。

## 二、核心领域模型（设计师必须理解的"名词表"）

所有界面都围绕这几个概念，请在视觉上为它们建立稳定的符号系统（颜色/图标/形状）。

### 1. 角色 Roles
| 角色 | 含义 |
|------|------|
| **Boss（老板）** | 消息接收/拍板方。可以是人，也可以是智能体。有权限 grant/revoke 对某些 agent 的访问。 |
| **Agent（智能体/员工）** | 干活并发消息的一方。每个 agent 有名字、身份 key、角色（如 orchestrator/worker）。 |
| **Session（会话）** | 一个正在运行的智能体实例，有实时状态（见下）。 |

### 2. 消息方向 Direction（3 种，需可视化区分）
- `agent_to_boss`　智能体 → 老板（汇报/提问/请批）
- `boss_to_agent`　老板 → 智能体（指令/回复）
- `agent_to_agent`　智能体 → 智能体（同级协作 / 上级审阅）

### 3. 消息模式 Mode
- `async`　发出即走，不等回复（进度/状态通知）
- `blocking`　发出后**等待回复**（提问 / 需要拍板）—— UI 上要强调"有人在等你"

### 4. 优先级 Priority（4 级，核心视觉信号）
`critical` › `high` › `normal` › `low`
> critical/high 会**同时推送到所有已配置渠道**；设计需有明确的紧急视觉层级（颜色/角标/震动/声音）。

### 5. 消息状态 Status（生命周期，需要状态机式可视化）
`sent` → `delivered` → `read` → `replied`　（旁路：`expired` 过期）

### 6. 渠道 Channel
`discord` · `telegram` · `api` · （`email` 保留但不内置）
> 客户端本身（macOS/iOS/Web）通过 `api` 渠道直连，与 Discord/Telegram 平级。

### 7. 选项消息 Options / Actions（**最重要的交互原语**）
智能体可以发一条带**选项按钮**的消息（如 "A / B / C" 或 "Approve / Reject"），老板点一个即回复。特性：
- **多端扇出**：同一条选项消息会同时出现在所有在线客户端 + Discord/Telegram。
- **谁先点谁赢**：全局唯一裁决，第一个选择者胜出，其余端立即收到 `resolved` 事件并**自动撤下该卡片**。
- **可过期**：带倒计时；过期后自动撤下，状态变 `expired`。
- 设计含义：选项卡片需要「实时出现 / 实时消失 / 倒计时」三态动画，且"被别处抢答"时要优雅退场。

### 8. 会话看板状态 Session Status（Kanban）
`working`（干活中）· `waiting`（等老板批准）· `blocked`（被外部阻塞）· `completed`（完成）
> 每个 session 附一句自述文本（"implementing feature"）。这是 Web 后台与 iOS 首页的核心数据。

### 9. 反应 Reactions（表情态）
👀 已看到 · 🔨 处理中 · ✅ 已完成——轻量状态确认，双向可用。

## 三、完整功能清单（按能力域组织，即"信息架构原料"）

以下是后端已实现的全部能力（来自 CLI v1.6.9），设计时据此规划各端的功能覆盖。**不是每个端都要全覆盖**——第四节给出分工建议。

### A. 消息收发
- 发送异步消息（带优先级 / 渠道 / 附件 / 类型标签）
- 发送**阻塞提问**（等回复，带超时倒计时）
- 发送**选项/动作消息**（按钮式拍板）
- 收件箱：未读 / 全部 / 按优先级 / 按发送方 / 全文搜索 / 未读计数
- 读取单条、回复（可带状态：accepted/completed/blocked）、加表情、查状态
- **编辑**已发消息、**转发**消息
- 附件：图片/文件上传（R2 存储），URL 附件

### B. 智能体协作（多智能体是第一性设计）
- Agent → Agent 直接发消息（`--to <label>`）
- 附带任务上下文 / 相关文件
- **智能体分组**：创建组、增删成员、**向整组广播**（可带优先级）
- **会话看板**：查看所有活跃会话及其 working/waiting/blocked/completed 状态

### C. 老板管理（权限体系）
- 老板列表 / 新增（人类 or 智能体）/ 详情 / 更新
- 绑定 Telegram user id、Discord user id
- **授权**：grant / revoke 某老板对某 agent 的访问
- 老板角色：admin 等
- 智能体作为老板：boss inbox（含优先级过滤/计数）、boss reply

### D. 路由与渠道
- 渠道配置：Discord（app-id/bot-token/webhook/channel-id）、Telegram（引导式配置）
- **按优先级路由**：如 `normal=discord, high=telegram`
- **规则路由**：按正则模式 + 目标 agent + 权重，把消息投递到指定处
- 渠道解析优先级：显式 `--channel` › 优先级路由 › 最近配置渠道兜底
- 免打扰时段（quiet hours）

### E. 智能体配置
- 默认优先级、限流（msg/min）、角色、按优先级的渠道路由

### F. 系统 / 运维
- init 初始化、config 读写、doctor 自检（连通性/渠道/路由）
- 后台 SSE 守护进程（daemon start/stop/status）——保证消息秒达
- Claude Code hooks 安装（会话级消息注入）
- 审计日志（audit）
- PWA / Service Worker（server 已内置一个极简 dashboard.html + manifest + sw.js，可作为 Web 后台起点）

## 四、三个设计交付端（本次全案范围）

> 另有一个**现存的 ESP32 圆屏硬件终端**（`terminal/`，LVGL + 圆形 LCD + 触摸），本次**不在** UI 设计范围内，仅作为生态背景告知。

### 端 1：macOS App —— "HiBoss Island"（重设计）

**现状**（需要在此基础上升级/重做视觉）：
- 一个原生 SwiftUI 应用，充当**老板端的实时接收器**。
- 已有两大界面：
  - **History（消息流）**：拉取最近 100 条消息，卡片列表，含方向/状态/优先级/时间。
  - **Settings（设置）**：Connection（服务器 URL + Keychain 里的 Boss Token）、Presentation（展示方式）、Alert（提醒声音）。
- 标志性交互 **"Island"（灵动岛式选项浮层）**：当收到带选项的消息，在**当前显示器顶部居中**弹出一个浮层（或普通可拖动窗口），老板点选项即回复；支持自由文本回复、过期倒计时、被抢答后撤下。
- 有**到达提示音**（可配置）、深色面板 chrome、过期倒计时条。
- 数据不本地持久化，纯实时 + 拉取。

**设计任务**：
- 重塑整体视觉语言（品牌化），统一到全案设计系统。
- 打磨"灵动岛浮层"这一核心差异化交互（出现/消失/倒计时/抢答退场的动效）。
- 优化 History 消息卡片的信息密度与状态可视化。
- Settings 结构化。菜单栏 Menu Bar Extra 常驻入口的视觉。

**关键界面清单**：灵动岛选项浮层（island 态 + window 态）· 消息流 · 单条消息详情 · 设置（连接/展示/提醒）· 菜单栏图标与下拉 · 空态/离线态/连接中态。

### 端 2：iOS 客户端（新立项，从 0 设计）

**定位**：老板"在路上也能拍板"的移动端。核心是**通知 + 秒回**，不是重管理。

**核心场景**：
1. 收到高优/紧急消息的**推送通知**（含选项按钮，可在通知上直接选/在锁屏快捷回复）。
2. 打开 App 看**待办拍板**（阻塞提问 + 选项消息，带倒计时）。
3. 消息流历史 + 单条详情 + 回复（文本/表情/选项）。
4. 会话看板（只读概览：哪些 agent 在 working/waiting/blocked）。
5. 多老板/多服务器切换（若用户管理多套）。

**建议信息架构（底部 Tab）**：
- **Inbox / 待拍板**（首页，突出 blocking & options & 未读计数徽标）
- **Messages / 全部消息流**（可搜索、按优先级/发送方筛选）
- **Sessions / 会话看板**（Kanban 只读）
- **Settings**（连接、渠道、通知偏好、免打扰时段、老板身份）

**关键界面清单**：
- 待拍板首页（卡片 + 倒计时 + 优先级色带）
- 选项消息交互卡（点选、被抢答撤下动画、过期态）
- 消息流 + 筛选/搜索
- 单条消息详情（含附件预览、状态时间线、reactions）
- 回复面板（文本 / 快捷表情 / 选项）
- 会话看板卡片
- 富通知样式（锁屏 / 横幅 / 通知内快捷操作）
- 设置各页 · 首次连接引导（输入 server + token / 扫码）
- 空态 / 离线 / 连接中 / 无权限

### 端 3：Web 管理后台（新立项，从 0 设计）

**定位**：桌面浏览器上的**指挥台 / 控制中心**。这是功能最全、最"重"的端，面向编排者与管理员。server 已内置一个极简 `dashboard.html` 作为占位，本次做全案。

**核心模块（左侧导航建议）**：
1. **总览 Dashboard**：活跃会话数、未读/待拍板计数、各渠道状态、最近消息流、优先级分布。
2. **消息中心 Messages**：全消息流，强筛选（方向/优先级/状态/发送方/渠道/全文搜索），单条详情抽屉，回复/转发/编辑，附件预览。
3. **会话看板 Sessions**：Kanban（working/waiting/blocked/completed）列，卡片含 agent 名 + 自述 + 最近活动；可直接对某会话发指令。
4. **智能体 Agents**：列表、配置（默认优先级、限流、角色、渠道路由）、身份 key 管理。
5. **智能体分组 Groups**：建组、成员管理、**整组广播**面板。
6. **老板与权限 Bosses & Access**：老板列表、绑定 Telegram/Discord id、grant/revoke 授权矩阵。
7. **路由规则 Routing**：优先级路由表 + 正则规则表（模式/目标/权重）的增删改。
8. **渠道 Channels**：Discord / Telegram 配置与连通状态、免打扰时段。
9. **审计 Audit**：操作/投递日志，可检索。
10. **系统 System / Doctor**：连通性自检、守护进程状态、服务器信息。

**关键界面清单**：
- 总览仪表盘（KPI 卡 + 实时消息流 + 图表）
- 消息表格/时间线双视图 + 筛选栏 + 详情抽屉
- Kanban 看板 + 会话卡 + 指令下发弹窗
- Agent 列表 + 配置表单
- 分组管理 + 广播 composer
- 权限授权矩阵（boss × agent 的 grant 关系，最好用矩阵/连线可视化）
- 路由规则编辑器（规则行 + 优先级路由映射）
- 渠道配置向导 + 状态灯
- 审计日志表
- 全局：登录/连接、空态、加载骨架、错误态、实时事件的 toast/badge 更新

## 五、跨端一致的设计要求

1. **实时性可见**：选项消息扇出/抢答/过期、会话状态变化、未读计数，都应有实时更新的微交互（SSE 驱动），不要"刷新才变"。
2. **状态符号系统统一**：Priority（4 级色）、Status（生命周期）、Direction（3 向）、Session（4 态）、Reactions（3 表情）在三端用同一套颜色/图标语义。
3. **紧急分级不打扰但不遗漏**：critical/high 有强信号（色/声/震），normal/low 安静。iOS 尤其要设计好通知分级 + 免打扰时段。
4. **深色优先**：目标用户长时间盯屏、多为开发者环境，深色为主、浅色可选，两套都要出。
5. **多智能体是第一性**：任何列表/消息都要清晰标出"是哪个 agent"。身份（名字 + 头像/色标）是一等公民。
6. **选项/拍板是招牌交互**：三端都要把"点一下就拍板"做到极致顺滑——这是产品差异点。
7. **自托管、无商业化**：不需要付费墙、订阅、计费、多租户等 SaaS 界面。定位是"给自己/团队用的工具"。
8. **可信赖的工具感**：信息密度可以高，克制而精确，避免消费级花哨；参考"专业指挥台/终端仪表盘"气质。

## 六、附录：消息数据字段参考（供设计标注真实字段）

单条消息（MessageResponse）主要字段：
`id` · `body`（正文）· `agent_name`（发送智能体）· `direction`（3 向）· `mode`（async/blocking）· `status`（生命周期）· `priority`（4 级）· `channel` · `metadata.options`（选项数组）· `metadata.options_expired` · `expires_at`（过期时间/倒计时）· `created_at` · `reactions`（表情列表）· 附件（图片/文件 URL）。

会话（Session）：`label`（会话名）· `status`（working/waiting/blocked/completed）· 自述文本 · 最近活动时间。

> ⚠️ 选项值是**结构化数组**，切勿用逗号推断选项边界——选项文案里可能带逗号，UI 需按数组逐项渲染按钮。
